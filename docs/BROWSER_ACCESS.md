## Recommended supported alternative: private GitHub Codespaces

No Codespace was created by this work. First check your GitHub account's Codespaces
included usage/spending settings. **Continue only within available free usage;stop
if GitHub requires paid usage.** Codespaces is a development environment,not a promise
of permanent free hosting. We did not verify your account's quota or eligibility.

1. Sign into GitHub in Chrome using the account that can access the repository.
2. Open https://github.com/parthivpatel-patel/GIG-C-Microstructure-Engine .
3. Select branch **feat/bootstrap-cpp20-engine**. Choose **Code → Codespaces → … →
   New with options** (wording varies). Confirm that branch and choose a2-core machine
   if offered within your free allowance. Do not choose main. On Android,Chrome's
   **Desktop site** can make the Codespaces controls easier to use.
4. Create/open the Codespace. The committed .devcontainer configuration installs
   Python3.12/C++ build tools/Node24 and runs scripts/setup_terminal.sh. Wait for
   **Setup complete** in the terminal;the initial native build may take several minutes.
   This builds existing engine code and frontend,no mock or market dataset.
5. In that Codespace's terminal run:

   ```sh
   bash scripts/start_terminal.sh
   ```

   Leave this process running. If setup did not run successfully,first run
   `bash scripts/setup_terminal.sh`,then retry startup. Errors fail explicitly;
   do not replace native output with a static demo.
6. Open the **Ports** tab beside Terminal. If8787 is missing,choose **Add Port** and
   enter `8787`. Verify **Port Visibility = Private**. Leave the internal port protocol
   **HTTP** (the backend is HTTP;GitHub supplies the external HTTPS connection).
   Do not change visibility to Public or Organization.
7. Click **Open in Browser** on8787,or copy its **Forwarded Address** into Chrome.
   On Android,open that exact address and sign into the same GitHub account.
   Do not copy the terminal's127.0.0.1 address. Your actual link is generated by GitHub,
   typically `https://YOUR-CODESPACE-NAME-8787.app.github.dev`.
   **That example is a pattern,not a URL we have provisioned or externally verified.**

The launcher derives the exact HTTPS Origin from documented Codespaces environment
variables and binds the container service0.0.0.0 only in that environment. It retains
Host/Origin restrictions and explicitly permits only corresponding HTTPS/WSS endpoints

Frontend,backend,assets and WebSocket use the same forwarded origin;only8787 is needed,

## Page loads but mutations/WS are denied

See [CODESPACES_ORIGIN_REPAIR.md](CODESPACES_ORIGIN_REPAIR.md). Stop the old server
before pulling/restarting;configure the exact HTTPS Origin,not wss or a trailing
slash. Current launcher and direct ASGI app share one Codespaces policy. The safe
/api/v1/connection endpoint exposes actual bounded Origin/Host/proxy diagnostics
without cookies/tokens. A rendering page alone does not prove a WS upgrade or
that the running process loaded newly pulled settings. No frontend/native rebuild
is required for this backend configuration repair.

If the actual WS Origin is rewritten to localhost despite a correct HTTPS policy,
use [CODESPACES_STREAM_PROOF.md](CODESPACES_STREAM_PROOF.md):pull,build only browser
assets,restart,refresh. Do not add localhost to the remote origin allowlist or trust
X-Forwarded headers. A strictly issued one-use stream proof binds the new browser's
connection to the configured HTTPS origin and distinguishes unrelated local probes.
